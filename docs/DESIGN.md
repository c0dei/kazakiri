# kazakiri の思想と設計

最終更新：2026-11-27

このファイルは「何を目指し、どう作っていて、なぜそうしたか」を書く。
使い方は [README](../README.md)、開発の手順は [DEVELOPMENT](DEVELOPMENT.md)、今後の課題は [IMPROVEMENTS](IMPROVEMENTS.md)。

## 1. kazakiri とは

数GB のログ・CSV・TSV・テキストを一瞬で開いて編集できる、Windows 向けの軽量テキストエディタ。
EmEditor の「大きいファイルが速い」体験を、買い切り不要のオープンソース（MIT OR Apache-2.0）で目指す。

| 項目 | 内容 |
|---|---|
| 対象 OS | Windows 10 / 11（コアは Linux でもテストする。画面は Windows 専用） |
| 主な用途 | ログ、CSV、TSV、txt。大きさは数GB |
| 言語・UI | Rust。Win32 + Direct2D / DirectWrite（GUI フレームワークなし） |
| 配布 | ポータブル版（zip）。インストーラーとコード署名は後回し |

## 2. 大事にしていること

迷ったときは、上にあるものを優先する。

1. **ファイルを壊さない。黙って変えない。**
   表せない文字は置き換えずに止める。保存は一時ファイルに書いてから置き換える。取り消せない操作（GREP 置換、ステータスバーからの変換保存）は確認し、バックアップを既定で残せるものは残す。編集中のファイルが外で変わっても、勝手に読み込まない。
2. **大きなファイルでも速い。**
   開く・表示・スクロール・検索のコストは、できるだけファイルの大きさに依存させない。大きなファイルは全体を読み込まない。
3. **画面を止めない。**
   時間のかかる処理は別スレッドで行い、進捗を出し、Esc で中止できるようにする。
4. **ほかのアプリの邪魔をしない。**
   ログを開いていても、書く側が追記・切り詰め・改名・削除をできることを目指す（残る制約は 5.2）。
5. **軽くて素直。**
   依存は小さく。ネットワーク通信・テレメトリはしない。設定はテキストファイル。
6. **Windows の作法に合わせる。**
   標準部品で成立する所は標準部品（キー操作・IME・読み上げ・DPI を OS に任せる）。ダークテーマで成立しない部品は自前で描く。目的は「標準部品にすること」ではなく、「本物の操作性」と「壊れないこと」。

### やらないこと（いまのところ）

- Windows 以外の画面
- 複数行にまたがる検索（一致は 1 行の中）
- 複数行にわたる状態を持つ構文解析（色分けは見えている行だけを見る）
- IDE 機能（言語サーバー、プロジェクト管理）
- プラグイン・スクリプト（操作の記録と再生のみ。Rhai の案は IMPROVEMENTS）

## 3. 全体の構成

```
kazakiri-win  （exe: kazakiri）        画面。Win32 + Direct2D。状態は App
   │  Document / Editor / Query などを呼ぶ
   ▼
kazakiri-core                         UI に依存しない。テスト・ベンチ可能
   ▲
kazakiri-cli  （exe: kazakiri-bench）  テストデータ生成と性能の計測
```

**分け方の規則**：ファイルの中身を扱う処理（読み込み、索引、編集、検索、変換、解析）は core に置き、画面なしでテストできるようにする。win は入力・描画・ダイアログ・非同期の受け渡しを担当する。

### core のモジュール

| モジュール | 内容 |
|---|---|
| `source` | ファイルの中身（メモリマップ、またはメモリに読み込んだ内容） |
| `encoding` | 文字コードの判定とデコード |
| `line_index` | 並列に作る、疎な行インデックス |
| `document` | 開いているファイル 1 つ。行の取り出し、カーソル移動、置き換え、書き出し、外部変更の確認 |
| `pieces` | ピーステーブル |
| `editor` | 元に戻す・やり直し、未保存の判定 |
| `search` / `grep` | ファイル内の並列検索、フォルダ内の検索と置換 |
| `convert` / `split` / `backup` | 文字コード・改行を変えて保存、分割・結合、バックアップと自動保存の置き場所 |
| `csv` / `diff` / `logtime` / `loglevel` | CSV の分割と並べ替え、行の差分、ログの時刻・レベル |
| `markdown` / `syntax` / `textops` | Markdown の解析、1 行ごとの色分け、文字列の変換と行の操作 |

### win のモジュール

一覧は `crates/kazakiri-win/src/app.rs` の先頭のコメント。大きく、入力（`input`・`command`）、寸法と描画（`layout`・`paint`）、機能ごと（`files`・`search`・`results`・`edit`・`csv_view` …）、部品（`tabs`・`toolbar`・`findrow`・`chrome`・各ダイアログ）に分かれる。
`settings` / `keymap` / `history` / `recent` / `session` は、`%APPDATA%` のファイルを読み書きする。

## 4. データの持ち方

```
Source（元のバイト列。書き換えない）
  ├─ LineIndex（元のファイルの行の位置。256 行ごと）
  └─ Pieces（編集後の姿。元の範囲と追加文字列の範囲の並び）
Document = 上の 3 つ + 文字コード + パス + 開いた時点の更新時刻（Arc で共有。複製が安い）
Editor   = いまの Document + 元に戻すための記録
```

- **Document は値のように扱う。** 編集は新しい `Document` を返す。別スレッドは `Arc<Document>` を受け取れば、その時点の内容を安全に読み続けられる。持ち主が 1 つだけのときは、その場で書き換えて複製を避ける（`edit_owned`）。
- **位置はバイト位置（u64）。** 行番号は必要なときに索引から求める。文字の境目は文字コードごとの規則で求める。
- **本文は元の文字コードのまま持つ。** デコードするのは表示・検索などで必要な範囲だけ。

## 5. ファイルの開き方

### 5.1 マップするか、読み込むか

`Source::open(path, memory_limit)`：

| 大きさ | 方法 | ほかのアプリができること |
|---|---|---|
| 上限以下（既定 64MB。設定「メモリに読み込む上限」、0〜1024MB） | メモリに読み込んで、ファイルを閉じる | 追記・上書き・切り詰め・削除・改名 |
| 上限より大きい | メモリマップ（読み取り専用） | 追記・上書き・削除・改名。**切り詰めは失敗する**（Windows のエラー 1224） |
| 0 バイト | メモリ（空はマップできない） | すべて |

GREP の走査（`open_scan_with`）は、すぐ閉じるので常にマップする。

**なぜ二通りか。** Windows は、マップされたファイルの切り詰めを拒否する。全部マップすると、`copytruncate` 型のローテーションや `>` での作り直しをするアプリが、kazakiri で開いているあいだ失敗する。全部読み込むと「大きいファイルが速い」と「省メモリ」が成り立たない。そこで大きさで分ける。小さなファイルは読み込んでも速く、メモリの負担も限られる。

検討して採らなかった案：

- マップをやめて必要な部分だけ読む（`ReadFile`）：本文を 1 本のスライスとして扱う索引・検索・編集の全体を作り直すことになる。
- 大きなファイルも一時ファイルに写してマップ：開くのに時間とディスクがかかる。
- 追従中だけ読み込みに切り替える：大きいログほどメモリが増え、挙動が分かりにくい。

**この方式の代償と残る制約**

- メモリは、読み込んだファイルの合計だけ増える（タブごと。上限 64MB のファイルを 10 個開けば約 640MB）。追記を読み込む瞬間は、新旧 2 つ分になる。
- 読み込みは画面のスレッドで行う。遅いドライブ（ネットワーク、USB）では、開くあいだ画面が止まる。前回のファイルの復元も、起動時にまとめて読む。
- 上限より大きいファイルは、従来どおり切り詰めできない。末尾の追従を始めるときに、その旨をステータスバーに出す。
- 追記で上限を超えたファイルは、そこからマップに切り替わる。
- 上限の変更は、次に開くファイルから反映する。

読み込んだ内容は外から変わらないので、副次的に、編集中のファイルを外で上書き・切り詰められても、編集中の内容は崩れない。マップしたファイルは、外で上書きされると、元の内容を指している部分も変わって見える。

挙動は `crates/kazakiri-core/tests/share_mode.rs` で確かめている。

### 5.2 外部の変更の検知

- 画面は 2 秒ごとに、表示中のタブのメタデータ（大きさ・更新時刻）を確認する（`Document::disk_state`）。
- 編集していなければ（未保存の編集がなければ）読み込む。**追記だけなら増えた分だけ**索引を伸ばす。メモリに読み込んだファイルは、ディスクからも増えた分だけ読む。
- 「追記」の判定は、先頭 4KB と、元の末尾 4KB が同じこと。途中だけを書き換えて、同時に追記された場合は、追記とみなす。
- 短くなった・書き換わった場合は開き直し、古い位置（選択、矩形・複数カーソル、全件検索の一覧など）を捨てるか範囲内に収める。
- 編集中は読み込まず、一度だけ知らせる。削除・移動も知らせる（内容は開いたまま）。

### 5.3 文字コードと改行

判定の順は、① BOM、② NUL の偏りから BOM なし UTF-16、③ 先頭 1MB が正しい UTF-8 なら UTF-8、④ Shift_JIS と EUC-JP をデコードしてみて、不正な文字などの点数で選ぶ。先頭 1MB しか見ないので、途中から別の文字コードになるファイルは検出しない。
改行は LF（CRLF を含む）が基本で、サンプルに CR しかなければ CR。

### 5.4 行インデックス

全行の位置は持たない。8MB のチャンクを最大 8 スレッドで並列に走査し、**256 行ごとの開始位置**だけを記録する。先頭から続けて終わった分はすぐ使えるので、開いた直後から表示できる。任意の行へは、直前の記録から数百行を `memchr` で進むだけで届く。
索引ができるまで、総行数は推定値で、編集はできない。

## 6. 編集と保存

- **ピーステーブル**：元の内容は書き換えず、「元の範囲」「追加した文字列の範囲」の並びで編集後を表す。各ピースが改行数を持つので、行番号と位置の変換は二分探索になる。
- ピースは配列で持つ。断片 12 万個で 1 回の編集が約 500µs と、キー入力で感じる遅さにならないので、平衡木にはしていない。すべて置換は専用の経路（`replace_many`）で、追加文字列を 1 つにまとめる。
- **元に戻す**：取り除いたピースを記録して差し戻す。記録の大きさは編集の大きさに比例する。続けた入力・削除はまとめる。最大 10 万件。
- すべて元に戻して元の内容になったら、ピーステーブルを捨てて「編集していない文書」に戻す（やり直しはできる）。これで外の変更を読み込めるようになる。読み込んだ時点で、やり直しの履歴は消える。
- **保存**（別スレッド）：必要ならバックアップ → 同じフォルダの一時ファイル（`.名前.kazakiri-save`）に書いて `sync` → 画面側で Document を手放して改名で置き換え → 開き直す。置き換えに失敗したら、一時ファイルを開いて場所を知らせる。開き直すので、保存すると元に戻す履歴は消える。
- **自動保存**（既定オフ）：未保存の内容を `名前.autosave` に全体を書き出す。元のファイルと履歴には触れない。

## 7. 検索

- 大文字小文字を区別する文字列検索は、検索語をファイルの文字コードに変換し、バイト列を `memchr::memmem` で探す（最速）。
- それ以外は `regex`。UTF-8 はバイト列のまま、ほかの文字コードは区切りごとにデコードして探す。
- ファイルを行の境目で区切って並列に探す。次／前の検索は、近くを 1 スレッドで探してから、範囲を広げながら並列で探す。
- **一致は 1 行の中に限る。** これで区切って並列にできる。

## 8. 画面の作り

### 8.1 状態とメッセージ

- 本体の状態は `App` 1 つで、スレッドローカルの `RefCell` に置く。ウィンドウプロシージャが借りて `handle` を呼ぶ。
- **借りている間に、メッセージが再び入ってくる操作をしない。** ダイアログやポップアップメニューは `Deferred` として返し、借用を外してから実行する（`deferred.rs`）。同期で届く描画の問い合わせ（ダークのメニューバー、ステータスバー、入力欄の色）は、借りる前に処理する。
- タブは、表示中の状態を `App` のフィールドに置き、ほかのタブの状態だけを出し入れする。描画や編集はタブを意識しない。

### 8.2 非同期の処理

別スレッドに `Arc<Document>` を渡す → 終わったら `PostMessageW` で結果（`Box` のポインタ）を画面へ返す。
中止は `AtomicBool`、進捗は `AtomicU64`。検索は番号を付け、古い結果は捨てる。
索引、検索、全件検索、置換、GREP、保存、並べ替え、差分、絞り込み、自動保存などがこの形。
行の操作・変換と行の統計は画面のスレッドで行うので、大きさに上限を設けている。

### 8.3 描画

見えている行だけを Direct2D / DirectWrite で描く。行のレイアウトは直前に描いた分をキャッシュする。
64KB を超える長い行は、横の位置に合わせた窓だけを取り出し、横の位置は「1 桁 ≒ 1 バイト」で扱う。
CSV の列の幅は、見えている行から決める。

### 8.4 標準部品と自前描画

| 部分 | 方式 |
|---|---|
| タイトルバー、メニューバー | 標準（ダークのメニューバーは `WM_UAHDRAWMENU` で塗る） |
| ステータスバー | 標準部品。色は各パートを自前描画 |
| 検索・置換・入力の行 | 標準の入力欄とボタン |
| 設定、GREP、キー割り当て | 標準部品を並べたウィンドウ（設定の背景は Direct2D） |
| スクロールバー | 標準（子ウィンドウ） |
| 本文、タブ、ツールバー、モードバー、結果一覧、コマンドパレット、16 進・差分・Markdown 表示 | 自前描画 |

タブとツールバーは、標準部品がダークテーマで成立しなかったので自前描画を続ける（経緯は [STANDARD_CONTROLS](STANDARD_CONTROLS.md)）。

ダークテーマの一部は `uxtheme.dll` の非公開関数（序数 133・135・136）を使う。見つからなければ明るいままになる。

## 9. 上限

固まる・メモリを使い切るのを避けるための上限。超えるときは、断るか打ち切って知らせる。

| 対象 | 上限 | 定義 |
|---|---|---|
| メモリに読み込むファイル | 既定 64MB（設定で 0〜1024MB） | `source.rs`、`settings.rs` |
| 1 行の表示用デコード | 64KB（超える行は窓で描く） | `document.rs` |
| クリップボードへのコピー | 256MB | `app.rs` |
| 全件検索の一覧 / すべて置換 / GREP | 100 万 / 1,000 万 / 20 万件 | `results.rs` |
| 行の操作・変換 1 回 | 64MB | `lines.rs` |
| 並べ替え（メモリ内） | 500 万行。超えると外部ソート（200 万行ずつ） | `csv.rs` |
| 差分 | 片方 300 万行、区間の違い 2 万件、記録 約 512MB | `diffview.rs`、`diff.rs` |
| 行の統計 | 500 万行 | `linestats.rs` |
| 時刻の範囲の抽出 | 256MB | `timefilter.rs` |
| 矩形選択 / 複数カーソル | 20 万行 / 1 万個 | `rect.rs`、`multi.rs` |
| Markdown プレビュー | 2MB | `mdview.rs` |
| 元に戻す | 10 万件 | `editor.rs` |

## 10. 書き込むファイルと、外部との関わり

| 場所 | ファイル |
|---|---|
| `%APPDATA%\kazakiri\` | `settings.ini`、`keys.ini`、`history.txt`、`recent.txt`、`session.txt`、`macro.txt` |
| `%TEMP%` | `kazakiri-start.log`（起動の経過）、`kazakiri-crash.log`（パニックの内容） |
| 対象のファイルの隣（または指定フォルダ） | `.bak`、`.autosave`、保存中の `.名前.kazakiri-save`、分割の `.partNNN` |

- ネットワーク通信はしない。Markdown のネットワーク上の画像も読まない。リンクは、クリックしたときだけ既定のアプリに渡す。
- レジストリは読むだけ（Windows のテーマなど）。管理者権限は要求しない。プロセス注入・フックはしない。

## 11. 性能の目標と守り方

| 項目 | 目標 |
|---|---|
| 1GB を開いて先頭を表示 | 0.1 秒以内 |
| 3GB の全行索引 | 2 秒以内（SSD） |
| 任意の行へのジャンプ | 1ms 以内 |
| 全文検索 | 1GB/秒以上 |
| 10GB を開いたときのアプリ固有メモリ | 200MB 以下 |

`tests/perf_guard.rs` が、128MB の合成ログで主な操作に時間の予算を設け、CI で確かめる（計算量の悪化を捕まえるためのもので、予算は実測の数十倍）。実測値は README と IMPROVEMENTS。
